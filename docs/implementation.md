# JanaMen: что сделано, ограничения и развитие

## 1. Реализовано

Бэкенд проверен скриптом `scripts/smoke.sh`.

| Контур ТЗ | Что сделано |
|---|---|
| Вход и роли | Вход по email и паролю (Sanctum, cookie), роли работник/руководитель/HR; доступ к командным и HR-разделам закрыт Gate, к заявкам Policy; лимит попыток входа |
| Личный кабинет | Профиль из read-модели 1С (ФИО, компания, должность, подразделение, руководитель, дата приёма, остаток отпуска), источник и время синхронизации, дашборд одним запросом |
| Заявка на отпуск | Валидация (дата не в прошлом, пересечения, остаток с учётом заявок в работе), цепочка руководитель → HR → подпись → подтверждено, отклонение с обязательным комментарием, отзыв, история переходов |
| Правила согласования | Руководитель согласует только прямых подчинённых; HR не согласует свою заявку; один человек не закрывает два шага одной заявки; нет доступного согласующего: заявка не создаётся |
| Мои заявки и очереди | Список своих заявок, карточка с историей и списком доступных действий (`available_actions` считает бэкенд), заявки команды руководителя, очередь и все заявки HR |
| Уведомления | Центр уведомлений: смена статуса заявки, назначение и завершение курса, ответ HR на обращение; счётчик для опроса, «прочитать» и «прочитать все» |
| Обращения в HR | «Сообщить о неточности в профиле» и эскалация вопроса из AI создают заявку-обращение, HR отвечает, автор получает уведомление |
| Jana Academy | Два курса из сидов, главы с материалом в Markdown и тестом, порог сдачи 70%, пересдача, прогресс, назначение курса сотруднику или подразделению, прогресс у руководителя и HR; правильные ответы наружу не отдаются |
| AI Jana | Ответы только по базе знаний (12 документов), источник со ссылкой на раздел, отказ при отсутствии ответа, фильтрация документов по роли, проверка ссылок на бэкенде, лог вопросов, эскалация в HR |
| Интеграции (моки) | Адаптеры 1С:ЗУП и Documentolog, журнал интеграций для HR |
| Локализация | Интерфейс ru/kz/en, язык хранится в профиле, бэкенд возвращает коды статусов и ошибок |

## 2. Смоделировано (моки)

| Что | Как смоделировано | Чем заменить |
|---|---|---|
| Кадровые данные 1С:ЗУП | Таблицы `mock_onec_employees` из JSON-фикстуры, чтение через `EmployeeDataSource` | `HttpEmployeeDataSource` + реальный адрес |
| Приказ об отпуске в 1С | Запись в `mock_onec_vacation_orders`, остаток уменьшается | HTTP-вызов в 1С, остаток вернёт следующая синхронизация |
| Документ на подпись Documentolog | Мок возвращает `document_ref`, запись в журнал | `DocumentSigningService` с реальным API |
| Подпись документов | HR подтверждает кнопкой «Документы подписаны» | webhook Documentolog |
| Контент курсов и регламентов | Вымышленные тексты из репозитория | Реальные документы компании |

## 3. Как подключить реальные системы

### 1С:ЗУП

Код приложения не зависит от того, мок это или реальная система: работает интерфейс `App\Integrations\Onec\EmployeeDataSource`.

1. В `backend/.env`: `HR_SOURCE=http`, `ONEC_URL=<адрес>`, `INTEGRATION_TOKEN=<токен>`.
2. `HttpEmployeeDataSource` уже обращается к `GET {ONEC_URL}/employees` и `POST {ONEC_URL}/vacation-orders` с заголовком `X-Integration-Token`. Формат тел описан в `docs/api.md` (раздел «Моки внешних систем»). Если реальная 1С отдаёт другой формат (OData, HTTP-сервис), преобразование делается внутри этого класса, остальной код не меняется.
3. Данные приходят в read-модель `employees`/`departments` командой `onec:sync`. Для продакшена: запускать по расписанию (Laravel Scheduler) и после отправки приказа (так уже сделано для одного сотрудника через `syncOne`).
4. Пользователи платформы связаны с сотрудником по `employees.external_id` (табельный номер). Правило остаётся: профиль только читается, правки вносятся в 1С.

### Documentolog

1. Реализовать второй класс `DocumentSigningService` (создание документа из шаблона «Приказ об отпуске», поля из заявки) и привязать его в `AppServiceProvider` вместо `MockDocumentSigningService`.
2. Принять webhook подписи: `POST /api/v1/webhooks/documentolog` с телом `{document_ref, status: "signed", signed_at}`. Он должен вызвать тот же переход `sign`, что сейчас вызывает HR кнопкой. Нужна проверка подписи или токена вебхука.
3. После подписи приказ уходит в 1С так же, как сейчас: слушатель `RunIntegrationsOnTransition` реагирует на статус `approved`.
4. Электронная подпись и хранение оригиналов остаются на стороне Documentolog, в платформе хранится только `document_ref`.

## 4. Известные ограничения

- Сбой интеграции (1С, Documentolog) логируется со статусом `error`, но автоматических повторов и кнопки «отправить заново» нет.
- Синхронизация 1С запускается при старте и вручную, расписания нет.
- Зависимости PHP ставятся при первом старте контейнера (нужен интернет), в образ они не запекаются.
- `message` в ошибках API только на русском; фронт строит тексты по `code`.
- База знаний и курсы только на русском, ответы AI на казахском и английском делает модель.
- Календарные дни без учёта праздников; один тип заявки (отпуск) полностью реализован.
- Уведомления обновляются опросом раз в 15–30 секунд, без WebSocket.
- Вопросы в AI уходят во внешний сервис OpenAI: для реальных данных нужна локальная модель или договорные гарантии обработки.
- Лимит попыток входа в примере окружения поднят для демо (по контракту 5 в минуту).

## 5. Что можно улучшить

**Надёжность:** очередь и повторы для интеграций, расписание синхронизации, запекание зависимостей в образ, healthcheck контейнера `app`, HTTPS и работа за reverse proxy.

**Безопасность:** сброс и смена пароля, SSO вместо парольного входа, аудит просмотров персональных данных HR, секреты через менеджер секретов, отдельный сервисный доступ для webhook.

**Качество:** feature-тесты доступа (чужая заявка, самосогласование, «два ключа»), сейчас их роль играет `scripts/smoke.sh`; Swagger через Scramble; CI с запуском тестов и сборки.

**Продукт:** заявка «Аванс» (каркас заявок готов: добавляется тип, форма и упрощённый маршрут), резервный согласующий для случая, когда согласовать некому, производственный календарь, редактор курсов и базы знаний для HR, email и Web Push для уведомлений, WebSocket вместо опроса.

**AI:** поиск по базе вместо передачи всей базы (эмбеддинги, когда документов станет много), оценка ответов 👍/👎 и раздел «вопросы без ответа» для HR (данные уже пишутся в `ai_messages`), казахская версия базы знаний, локальная модель для персональных данных.

## 6. Допущения

Данные вымышленные; организационная структура в сидах покрывает все варианты маршрута согласования (директор без руководителя, руководитель HR-отдела с ролью HR, три HR для правила «двух ключей»); цифры в регламентах и курсах придуманы для демонстрации.
